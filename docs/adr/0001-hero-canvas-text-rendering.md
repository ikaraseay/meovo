# Hero 文案用 Canvas 渲染，DOM 原文保留为唯一无障碍副本

Hero 的标题和副标题改由 Canvas 绘制，DOM 里的原文**不删不改**，只是让出颜色。
两者是同一份文案的两种呈现：DOM 那份是唯一的无障碍与可选取来源，Canvas 那份是视觉层。

**为什么不直接用 DOM 渲染？** 流体光标要求每一帧按光标位置重新计算文案的几何形状
（哪些字在障碍物左边、哪些在右边），DOM 做不到 —— 每帧改 DOM 会触发回流，
而且浏览器没有「让文字绕开一个动态圆形障碍物」这种排版能力。Canvas + 预排版引擎
（Pretext）才能做到。

**为什么不把 DOM 原文删掉？** 删掉之后屏读器读不到、搜索引擎抓不到、
读者也选不中这段文字。所以保留它，用 `opacity: 0` 让出颜色而不是 `visibility: hidden`
或 `display: none` —— 前者选不中，后者会让版面塌陷（高度归零，下方内容上移）。
`opacity: 0` 在 Chrome 里仍留在无障碍树与焦点顺序中，屏读器照常朗读。

**DOM 怎么和 Canvas 对齐？** 岛屿会把 DOM 那份的 `text-wrap` 强制成 `wrap`
（Hero 原标题用了 `text-wrap: balance`，浏览器的平衡断行和 Pretext 算出来的不一致），
让两边的行断点相同。

**代价（明确接受）**：文字在 Canvas 上不可被浏览器「查找」、不可被划词工具命中，
选中时高亮框与 Canvas 实际排版可能不完全对齐；DOM 里的 `text-wrap: balance`
等 CSS 排版属性对 Canvas 那份无效。

**Consequences**: Hero 的文案在 Canvas 上重绘，DOM 里的那份高度只决定版面占位。
当前实现是「劈开不重排」——行断点固定，只把被光标切到的那一行从中间劈开，
所以行数与总高度恒等于自然排版，页面不会跳，**不需要**按最坏障碍物位置预留高度。
若日后改成「走廊重排」（文字绕开障碍物重排、可能多出一行），
那时才必须按最坏位置算预留高度，否则光标经过时会撑高 Hero、把下方内容顶走。
